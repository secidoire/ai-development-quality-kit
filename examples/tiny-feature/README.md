# 架空評価例: 顧客検索画面

## 概要

検索画面に、共通部品`SearchBox`、画面`CustomerSearchPage`、カスタムフック`useCustomerSearch`がある想定。

設計書には次がある。

- `SCR-CUST-001`: 検索語が2文字未満なら検索ボタンを非活性にする。
- `SCR-CUST-002`: 検索APIが失敗したら画面上部にエラーを表示する。
- `SCR-CUST-003`: 検索結果行から詳細画面へ遷移する。

責任分界メモでは次を候補とする。

- `SearchBox`: 入力欄とボタン表示、propsで受け取ったdisabled表示。
- `CustomerSearchPage`: 画面としての表示構成と遷移。
- `useCustomerSearch`: 検索語長、API呼び出し、エラー分類。

## 評価意図

`scripts/trace_check.py`で、次を機械的に検出できることを確認する。

- 未リンク設計項目。
- 存在しないテストID。
- 実行証拠の設計版違い。
- 未実行/失敗。
- 孤立テスト。

意味的に「期待値が設計を満たすか」は、このチェッカーでは証明しない。

テストコード品質の評価では、`SCR-CUST-001`に対して「検索語1文字で非活性」「2文字で活性」という境界値だけでなく、実際の利用者が検索語を入力し、結果やエラーを見る使われ方を主テストとして扱う。coverageを満たすためだけに内部関数やmock呼び出しを確認するテストは、補助にもならない場合がある。

このチェッカーはJSONインベントリを照合するだけで、実テストファイルやrunnerを探索しない。`MISSING_TEST`は「一覧に無い」という意味であり、ファイルを実読して不存在を証明したものではない。exit code `0`は機械的errorが無いことだけを示し、意味的品質や顧客承認を意味しない。
